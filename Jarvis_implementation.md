# Джарвис: локальный голосовой ассистент

## 1. Общая архитектура

Проект реализует локальный голосовой конвейер:

```text
Микрофон
   ↓
AudioStream
   ↓
openWakeWord
   ↓
CommandRecorder
   ↓
PCM audio
   ├──→ WeSpeaker → идентификатор пользователя
   │
   └──→ Whisper.cpp → текст команды
                    ↓
                   LLM
                    ↓
                  ответ
                    ↓
                  Piper
                    ↓
               воспроизведение
```

Основная идея оптимизации заключается в том, чтобы не создавать отдельные аудиопотоки и не запускать тяжёлые модели заново для каждой команды. Аудио после записи остаётся в памяти и передаётся между модулями без промежуточных файлов там, где это уже поддерживается используемыми библиотеками.

---

# 2. Файлы проекта

## `config.py`

Файл содержит основные настройки аудиосистемы и пороговые значения.

### Основные параметры

- `SAMPLE_RATE = 16000` — частота дискретизации микрофона.
- `CHANNELS = 1` — используется один аудиоканал.
- `CHUNK_SIZE = 1280` — размер блока аудио, получаемого от микрофона.
- `DURATION = 5` — длительность записи в старой логике проекта.
- `SILENCE_THRESHOLD = 500` — порог громкости для определения речи.
- `SILENCE_DURATION = 0.5` — команда считается законченной после примерно 0,5 секунды тишины.
- `SILENCE_CHUNKS` — количество аудиоблоков, соответствующее заданной длительности тишины.
- `WAKE_WORD_THRESHOLD = 0.5` — порог срабатывания модели wake word.
- `SPEAKER_THRESHOLD = 0.6` — минимальная похожесть для идентификации пользователя.
- `AUDIO_DEVICE = 1` — используемое устройство записи.

### Почему настройки вынесены отдельно

Это позволяет менять параметры без изменения логики отдельных модулей. Например, если микрофон изменится, достаточно поменять `AUDIO_DEVICE`.

---

## `audio.py`

Модуль отвечает за создание единого аудиопотока.

Используется `sounddevice.InputStream`.

Главное изменение архитектуры заключается в том, что поток создаётся один раз:

```python
start_audio(callback)
```

и передаёт получаемые от микрофона блоки в callback.

### Почему это важно

Ранее разные этапы могли последовательно создавать и закрывать свои `InputStream`. Это добавляло задержку между обнаружением wake word и началом записи команды.

Теперь микрофон работает через один постоянный поток:

```text
микрофон → InputStream → callback
```

а текущий этап обработки определяется состоянием pipeline.

---

## `wake_word.py`

Модуль отвечает за обнаружение ключевой фразы.

Используется `openWakeWord`.

Модель загружается один раз:

```python
model = Model(inference_framework="onnx")
```

Функция:

```python
detect(audio)
```

получает очередной блок PCM-аудио и проверяет оценку модели `hey_jarvis`.

Порог берётся из:

```python
cfg.WAKE_WORD_THRESHOLD
```

### Почему модель загружается один раз

Загрузка модели является более тяжёлой операцией, чем обработка отдельного аудиоблока. Поэтому модель создаётся при импорте модуля и затем переиспользуется.

---

## `command_record.py`

Модуль отвечает за запись голосовой команды после обнаружения wake word.

Основной класс:

```python
CommandRecorder
```

Он хранит:

- полученные аудиоблоки;
- информацию о том, началась ли речь;
- количество последовательных тихих блоков;
- состояние завершения записи.

### Логика завершения

Для каждого блока рассчитывается средняя амплитуда:

```python
volume = np.abs(audio).mean()
```

Если громкость выше `SILENCE_THRESHOLD`, считается, что пользователь говорит.

После начала речи программа считает тихие блоки.

Когда их количество достигает `SILENCE_CHUNKS`, запись завершается.

### Почему длительность тишины уменьшена

Используется:

```python
SILENCE_DURATION = 0.5
```

Вместо ожидания более длительной паузы ассистент заканчивает запись примерно через полсекунды тишины.

Это уменьшает задержку перед STT.

---

## `speaker.py`

Модуль отвечает за идентификацию пользователя по голосу.

Используется `WeSpeaker`.

### Основные этапы

1. При запуске загружается модель.
2. Эмбеддинги эталонных записей пользователей рассчитываются один раз.
3. Для новой команды строится embedding.
4. Он сравнивается с эталонными embeddings.
5. Выбирается пользователь с максимальной похожестью.
6. Если максимальная похожесть ниже `SPEAKER_THRESHOLD`, пользователь считается неизвестным.

### Оптимизация PCM

Ранее для получения embedding использовался WAV-файл.

Теперь аудио команды передаётся непосредственно из памяти.

Перед вызовом WeSpeaker NumPy-массив преобразуется в `torch.Tensor`, потому что `extract_embedding_from_pcm()` ожидает именно tensor.

Таким образом:

```text
CommandRecorder
      ↓
numpy.ndarray
      ↓
torch.Tensor
      ↓
WeSpeaker
```

Промежуточный WAV для WeSpeaker больше не нужен.

---

## `stt.py`

Модуль отвечает за Speech-to-Text.

Используется `whisper.cpp` через Python binding `pywhispercpp`.

### Предыдущая реализация

Ранее Python запускал:

```text
whisper-cli.exe
```

через `subprocess`.

Каждый вызов приводил к запуску нового процесса и повторной загрузке модели.

Это было одним из основных источников задержки.

### Текущая реализация

Модель создаётся один раз:

```python
model = Model(...)
```

После этого функция:

```python
transcribe(audio)
```

получает аудио непосредственно из памяти.

Перед передачей в Whisper PCM преобразуется из `int16` в `float32`:

```python
audio.astype(np.float32) / 32768.0
```

### Новая схема

```text
CommandRecorder
      ↓
numpy audio
      ↓
Whisper
      ↓
текст
```

`command.wav` больше не нужен для STT.

---

## `tts.py`

Модуль отвечает за преобразование текста ответа в речь.

Используется Piper и модель:

```text
ru_RU-dmitri-medium.onnx
```

### Оптимизация

Ранее Piper запускался через CLI с помощью `subprocess`.

Теперь используется Python API:

```python
voice = PiperVoice.load(...)
```

Модель загружается один раз при запуске.

Функция:

```python
synthesize(text)
```

создаёт WAV непосредственно в памяти через `io.BytesIO`.

### Почему это быстрее

Не создаётся новый процесс Piper для каждого ответа и не требуется сохранять промежуточный WAV-файл на диск.

Результат функции:

```text
bytes
```

передаётся непосредственно в модуль воспроизведения.

---

## `player.py`

Модуль отвечает за воспроизведение результата TTS.

Он получает WAV в виде `bytes`, помещает его в `BytesIO`, декодирует через `soundfile` и воспроизводит через `sounddevice`.

Схема:

```text
Piper
 ↓
WAV bytes
 ↓
BytesIO
 ↓
soundfile
 ↓
sounddevice
```

Отдельный файл с результатом TTS не требуется.

---

## `pipeline.py`

Это основной управляющий модуль проекта.

Он объединяет все компоненты.

### Состояния

Используются два основных состояния:

```text
waiting
recording
```

В состоянии `waiting` каждый аудиоблок передаётся в openWakeWord.

После обнаружения:

```text
hey jarvis
```

состояние переключается на:

```text
recording
```

и создаётся `CommandRecorder`.

После определения конца речи pipeline получает готовое PCM-аудио.

### Обработка команды

Дальше выполняются:

```text
audio
 ↓
WeSpeaker
 ↓
user
```

и:

```text
audio
 ↓
Whisper
 ↓
text
```

После этого сейчас используется тестовый ответ:

```python
response = "Я получил твою команду."
```

В дальнейшем этот участок заменяется вызовом LLM.

После получения ответа:

```text
response
 ↓
Piper
 ↓
audio bytes
 ↓
player
```

# 3. Почему была изменена архитектура

Основная проблема старой реализации заключалась не в отдельных моделях, а в способе их соединения.

Раньше происходило много лишних операций:

```text
создать InputStream
↓
обработать
↓
закрыть InputStream
↓
создать следующий InputStream
```

и:

```text
запустить процесс
↓
загрузить модель
↓
обработать
↓
закрыть процесс
```

Для голосового ассистента это особенно заметно, потому что модели openWakeWord, WeSpeaker, Whisper и Piper достаточно тяжёлые.

Новая архитектура использует принцип:

> тяжёлые ресурсы загружаются один раз, а небольшие аудиоблоки и результаты обработки передаются между модулями.

---

# 4. Что было оптимизировано

## Аудиопоток

Было:

```text
несколько InputStream
```

Стало:

```text
один InputStream
```

Это уменьшает задержку после wake word.

## WeSpeaker

Было:

```text
audio → WAV → WeSpeaker
```

Стало:

```text
audio → Tensor → WeSpeaker
```

Кроме того, embeddings эталонных голосов рассчитываются один раз.

## Whisper

Было:

```text
Python
 ↓
subprocess
 ↓
whisper-cli.exe
 ↓
загрузка модели
 ↓
STT
```

Стало:

```text
Python
 ↓
уже загруженная модель
 ↓
STT
```

## Piper

Было:

```text
Python
 ↓
Piper CLI
 ↓
загрузка модели
 ↓
TTS
 ↓
WAV
```

Стало:

```text
Python
 ↓
уже загруженная модель
 ↓
TTS
 ↓
WAV bytes
```

## Передача аудио

Где возможно, промежуточные файлы убраны.

Основной обмен теперь идёт через память:

```text
numpy.ndarray
torch.Tensor
bytes
```

# 6. Текущий полный конвейер

После запуска `pipeline.py`:

```text
1. Загружаются модели:
   ├── openWakeWord
   ├── WeSpeaker
   ├── Whisper
   └── Piper

2. Запускается один InputStream.

3. Ассистент ждёт:
   "Hey Jarvis"

4. После обнаружения начинается запись команды.

5. После ~0.5 секунды тишины запись заканчивается.

6. Полученное PCM-аудио передаётся:
   ├── WeSpeaker → определение пользователя
   └── Whisper → распознавание команды

7. Формируется ответ LLM
   (сейчас используется тестовая строка).

8. Piper превращает ответ в WAV bytes.

9. Player воспроизводит ответ.
```

---

# 7. Что осталось на будущее

Текущая реализация является рабочим прототипом. Для следующего этапа можно отдельно улучшить:

- VAD вместо простого определения громкости;
- обработку нескольких команд без перезапуска pipeline;
- выполнение тяжёлого inference вне audio callback;
- обработку ошибок моделей;
- подключение реальной LLM вместо тестового ответа;
- подавление информационных сообщений сторонних библиотек.

Эти изменения намеренно не включены в текущую оптимизацию, чтобы не усложнять рабочий прототип без необходимости.

---

# 8. Результат работы

В результате получен локальный голосовой pipeline, в котором:

- микрофон используется через единый поток;
- wake word работает непрерывно;
- запись команды завершается автоматически по тишине;
- пользователь определяется по голосу;
- STT работает через whisper.cpp;
- TTS работает через Piper;
- тяжёлые модели загружаются один раз;
- передача аудио между основными этапами выполняется через память;
- временный WAV больше не используется для передачи аудио между WeSpeaker и STT;
- текущий pipeline можно запускать локально без сетевых сервисов.

Таким образом, текущая версия уже соответствует основной идее локального голосового ассистента: аудио поступает с микрофона, проходит через цепочку распознавания и идентификации, а результат возвращается пользователю голосом.


# 9. Отключение технических логов Whisper

`whisper.cpp` выводит служебную информацию при загрузке модели непосредственно из нативного C/C++ кода. Поэтому обычные настройки `print_progress=False` и `print_realtime=False` не убирают сообщения вида:

```text
whisper_model_load: loading model
whisper_backend_init_gpu: ...
whisper_init_state: ...
```

Чтобы консоль оставалась чистой, в `stt.py` стандартный файловый дескриптор `stderr` временно перенаправляется в `os.devnull` только на время загрузки модели.

После завершения `Model(...)` исходный `stderr` восстанавливается. Ошибки Python и остальной программы при этом не скрываются.

Итоговая схема загрузки Whisper:

```text
stt.py запускается
      ↓
временно скрываем native stderr
      ↓
загружаем модель Whisper
      ↓
восстанавливаем stderr
      ↓
pipeline продолжает работу
```

Это влияет только на вывод служебных сообщений и не отключает сам Whisper и не меняет качество распознавания.
